# D20 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a 20-sided die: a D20 tab on the Viewer's stage, a D20 option on the Sender's QR switch, and a `view=d20` die page. Its numbering is fixed so a real 20-sided box can be numbered to match.

**Architecture:** The D20 is 20 CSS-3D triangles inside the existing rotating `.model-3d`, so it moves with the same transform and transition as the cube. The cube's top-face logic is generalised to any die described by a table of outward face normals plus a hysteresis constant (`DICE`). The die page and Sender switch learn a second die kind, `d20`, alongside `die` (the cube, labelled D6).

**Tech Stack:** One static `index.html` (CSS, markup, one inline script); `tests/harness.test.js` (Node `vm` + fake DOM, `npm test`).

**Spec:** `docs/superpowers/specs/2026-11-26-d20-design.md`

## Global Constraints

- One static file, no build step, no new libraries. Protocol and payload unchanged.
- Stored values: `gyrolink_viewer_model` is `phone` | `die` | `d20`; `gyrolink_sender_link` is `viewer` | `die` | `d20`. `view=die` opens the cube, `view=d20` the D20. Anything else falls back to Phone / Viewer / the normal app.
- Labels: Viewer stage **Phone | D6 | D20**; Sender switch **Viewer | D6 | D20**. Element ids keep `die` for the cube (`btn-model-die`, `btn-link-die`).
- D20 numbering: opposite faces add up to 21; face 1 outward normal +z, face 20 −z (device axes); a corner of 20 lies along +y; every corner's five faces sum to 52 or 53.
- Hysteresis ≈ 3° at an edge: cube `0.08`, D20 `0.04`.
- Share title and die-page tab title stay "Die" for both dice.
- User-visible strings from payloads use `textContent` (the D20's face numbers are static markup).
- Work on branch `d20`; commit per task; do not push to `main` (it deploys) without the user's go-ahead.
- `npm test` passes and the README is updated in the same change.

## Review Focus

1. CSS that hides the number readout or the D20's faces on the D20 tab, because today's rules key on `data-model="die"`. Expected: D20 shows the d20 faces and the readout. Pinned by Task 1's CSS visibility test.
2. Switching D6 ↔ D20 mid-stream carries the old die's face number into the new die's hysteresis. Expected: the new die's correct number, immediately. Pinned by Task 1's carry-over test.
3. The box resting on a D20 corner (five faces meet) jitters by a degree. Expected: the number holds. Pinned by Task 1's corner test.
4. A saved or linked value that isn't a known kind (`foo`, `toString`). Expected: Phone / Viewer, no crash, and `DICE[value]` never matches an inherited property. Pinned by Task 1 (model) and Task 2 (link).
5. The `view=d20` page changes the phone's own Viewer choice. Expected: nothing saved, and the normal Viewer keeps its model. Pinned by Task 2's die page test.
